# 品質ルール（8カテゴリ・45項目）

## 1. Claude Code記述 / Codex監査（5項目・2026-09-07 役割反転）

1. HTML/CSS/JS の記述は Claude Code（CEOブース・制作ブース）が行う。Codex への記述委託は行わない
2. Codex の役割は「監査専任」。コードの記述・修正は行わない。指摘のみを返す
3. Codex監査は次の3点を対象とする — (a) rules.md 全カテゴリ準拠 / (b) レスポンシブ規則（カテゴリ4の全アスペクト比ルール含む） / (c) アクセシビリティ・SEO基本項目
4. 監査タイミングは「サイト完成単位」（Yuichi決定 2026-09-07）。commit 毎の監査は行わず、1サイトの制作完了時点で1回実施する
5. 監査で指摘された修正は Claude Code が実施する。再監査は重要度「高」の指摘があった場合のみ行う

### Codex監査レポート形式（固定）

| 指摘項目 | 該当ファイル・行 | 違反ルール番号 | 重要度 |
|---|---|---|---|
| （指摘の要約） | `index.html:120` | 37 | 高 |

重要度の基準 — **高**: 表示崩れ・機能不全・アクセシビリティ阻害 / **中**: ルール違反だが実害限定 / **低**: 表記ゆれ・改善提案

### 変更しないもの

- 画像生成の Codex 担当（cx-image / 制作ブース2）は従来どおり Codex が行う。今回の反転はコード記述のみ
- Kimi の担当（日本語コピー・リサーチ）は変更しない

## 4. CSS品質（45項目・2026-09-07 全アスペクト比レスポンシブ10項目 + iOS実機検証由来4項目 / 2026-09-09 デザイン層10項目を追加）

18. CSS変数を統一使用する（--bg / --bg-alt / --bg-dark / --text / --text-mid / --text-light / --accent / --line / --r）
19. CSS変数の値をハードコードしない
20. **禁止フォント：Inter / Arial / Roboto / Helvetica は使用禁止**
21. アニメーションは transform と opacity のみ使用する（top/left/marginのアニメーション禁止）
22. セクション間padding: 120px（desktop）/ 72px（mobile）
23. border-radius は var(--r) で統一する
24. 横線で区切る — セクション間に 1px solid var(--line)
25. 彩度を抑える — ビビッドな色は使わない
26. prefers-reduced-motion に対応する
27. !important は使用禁止（noscript内を除く）
28. 日本語フォントの全ウェイト読み込み禁止（最大3ウェイト：300/400/500）
29. CSS/JSの外部ファイル分離禁止（スタンダード時）
31. word-break: keep-all を適用する要素は、親コンテナの幅制限を確認する。狭いカード（300px以下）内では overflow-wrap: anywhere を併用する。テキストカードのグリッドは最大3列。
32. **`.section-heading` の `align-items` は必ず `start` を使用する（`end` 禁止）**。`end` を使うと段落がh2より上に浮き上がるレイアウトバグが発生する。
33. **portrait / profile 画像には必ず `max-height: 420px` を設定する**。列幅が広いと縦に伸びすぎてバランスが崩れる。
34. **2カラムグリッド（company-grid / contact-grid 等）は `align-items: stretch` を使用する**。`start` では左右の下端が揃わない。
35. **全 `<img>` タグに `width` と `height` 属性を必ず設定する**（hero含む）。未設定は CLS（累積レイアウトシフト）の原因になり Lighthouse スコアを低下させる。
36. **`html` と `body` の両方に `overflow-x: hidden` を必ず設定する**。`body` だけでは Safari iOS でマーキー等の `width: max-content` 要素がページ幅を膨張させ、コンテンツが画面左半分に寄り右半分が空白になるバグが発生する。Chrome / Puppeteer では再現しないため実機確認が必須。
37. **CSS Grid の `grid-template-columns: 1fr` は `minmax(0, 1fr)` で書く**。`1fr` は `minmax(auto, 1fr)` の略であり、アイテムの min-content がコンテナ幅を超えるとトラックが膨張し水平オーバーフローを起こす。モバイルブレークポイント内・セクションラッパーの単一列定義は全て `minmax(0, 1fr)` にする。
38. **`display: grid` を持つセクションラッパーには `grid-template-columns` を必ず明示する**。省略すると暗黙の auto トラックがアイテムの max-content 幅で確定し、コンテンツが画面幅を超えてもクリップされない。`display: grid;` と書いたら必ず次行に `grid-template-columns: minmax(0, 1fr);` を書く。
39. **flex コンテナ内に `display: grid` を持つ要素は `min-width: 0` を追加する**。flex アイテムのデフォルト `min-width: auto` はアイテムの min-content で決まるため、内部の grid が想定より広い幅を要求するとコンテナが押し広げられる。

### 全アスペクト比レスポンシブ（40〜49 / 2026-09-07 追加）

40. **`box-sizing: border-box` を `*, *::before, *::after` に必ず適用する**。padding/border を含めた幅計算にしないと、幅指定要素が親をはみ出す。
41. **`100vh` の単独使用禁止**。`height: 100vh;` の直後に `height: 100dvh;` を併記してfallbackとする。iOS Safari のアドレスバー分だけ実表示領域がずれ、ヒーローが画面外に押し出される。
42. **`100vw` 使用禁止**。`100vw` はスクロールバー幅を含むため、縦スクロールのあるページで必ず横にはみ出す。`width: 100%` を使う。
43. **コンテナに固定px幅を指定しない**。`max-width: 1200px; width: 100%;` の組み合わせのみ許可する。`width: 1200px` は狭いビューポートで即オーバーフローする。
44. **`img` / `video` には `max-width: 100%; height: auto;` を必ず設定する**。加えてCLS防止のため `aspect-ratio` またはHTMLの `width` / `height` 属性を明示する（35と併せて運用）。
45. **見出し・大きめフォントと主要余白は `clamp()` で流体化する**。例: `font-size: clamp(1.75rem, 4.5vw, 3rem);` / `padding: clamp(48px, 8vw, 120px) 0;`。ブレークポイントごとの固定値切り替えだけでは中間幅で破綻する。
46. **grid のトラック定義は `minmax(0, 1fr)` を必須とする**（37の再確認）。`1fr` は `minmax(auto, 1fr)` の略であり、min-content がコンテナ幅を超えるとトラックが膨張する。
47. **日本語長文見出しには `overflow-wrap: break-word` を必須とする**。改行位置の指定は既存の文節ルール（`word-break: keep-all` + 31）に従い、破綻時の逃げ道として break-word を併用する。
48. **`position: fixed` / `sticky` 要素は `env(safe-area-inset-*)` に対応する**。例: `padding-bottom: calc(16px + env(safe-area-inset-bottom));`。iPhone のホームインジケータ・ノッチに固定CTAやヘッダーが重なる。
49. **table・コードブロック等の横長要素は、その親に `overflow-x: auto` を付与する**。`body` 側の `overflow-x: hidden`（36）に依存して隠すのは禁止。隠すのではなく、その要素の中でスクロールさせる。

### 日本語の改行制御（62〜64 / 2026-09-09 追加）

> カテゴリ9（日本語コピー品質・15項目）には自動検査が一つもなかった。
> `tools/check-copy.js`（qa-check.sh ⑧）で機械判定できる項目を検査する。
> 文体レベル・主語の重複・具体性テストは主観のため機械判定しない。

62. **`body` に `line-break: strict` を設定する**。`overflow-wrap: anywhere`（mobile-safety 必須ブロック）は禁則を無視して折り返すため、長音符「ー」・促音「ッ」・句読点が行頭に孤立する。`line-break: strict` は **min-content 幅を変えないので、`keep-all` と違い横はみ出しを起こさずに禁則だけを回復できる**。実測: 8サイトで行頭孤立 6件 → 2件、横はみ出しは0件のまま。
63. **`word-break: keep-all` は h1 / h2 までにとどめる**。h3 以下はグリッド内の小見出しが多く、keep-all を当てると 320px で溢れる（mori 実測 294px > 288px）。`overflow-wrap: break-word` は **min-content 幅を縮めないため回避できない**（縮めるのは `anywhere` だけ）。h3 以下の禁則は 62 で担保する。
64. **h1 / h2 には `word-break: keep-all` と `overflow-wrap: break-word` を併記する**。`normal` だと収まらない見出しがそのまま溢れる（forge 実測 393px > 390px / mori 594px > 430px）。`break-word` なら通常は文節で改行し、溢れる場合だけ語中で折り返す。

### デザイン層の追加ルール（65〜74 / 2026-09-09 追加）

65. **デザイン用の追加CSSは、mobile-safety のメディアクエリより「前」に挿入する**。`</style>` の直前に足すと、末尾にある `@media (max-width: 768px) { .section-number { font-size: 12px } }` などの安全ルールを打ち消す。メディアクエリは詳細度を上げないため、後ろに書いたルールが無条件に勝つ。実測: bloom で末尾に足したところ section-number が 10.56px になり、モバイル検査が9件失敗した（挿入位置を変えるだけで0件）。
66. **横スクロールする文字列（マーキー）を使わない**。`animation: marquee ... linear infinite` で流れるキーワード帯は、読ませる情報がないのに視線を奪い続ける。装飾のためだけに `width: max-content` を作るため 36 の横はみ出しリスクも抱える。2026-09-09 に7サイトから全撤去した。既存の装飾ルール 54〜58 と同じ扱いとする。
67. **セクション見出しの大型化は「英字のディスプレイ語」に限る**。`Concept` / `Works` のような1〜2語の英字見出しは `clamp(2.4rem, 6.4vw, 4.5rem)` まで上げてよい。**日本語の文を h2 に置いているサイト（akari / mori / tomori）には適用しない** — 文の見出しを72pxにすると1行が数語しか入らず、可読性も改行位置も壊れる。適用可否は「見出しが語か、文か」で判断する。
68. **写真の上に情報パネルを重ねない**。半透明の帯や `backdrop-filter: blur()` のカードを写真に載せると、写真を隠すうえ文字の背景が読み手側で予測できない。価格・営業時間・最寄駅のような「読ませる事実」は、写真から出して地の文として置く。2026-09-09、tomori の `.floating-card`（コース価格と最寄駅を夜のテーブル写真に重ねていた）を撤去した。**7 のカード判定は `border-radius` を必須にしているため角丸なしのパネルはすり抜ける** — check-style ⑨ で別に判定する。
69. **制作側の用語を公開ページに出さない**。`Final CTA` / `Hero` / `Section 3` / `Above the fold` などは社内の呼び名であり、来訪者には意味がない。tomori は他セクションが `Story 01` 〜 `Reservation 05` と番号で揃っているのに、最後だけ `Final CTA` が出ていた。eyebrow / kicker に置く語は、来訪者がそのまま読んで意味が通るものに限る。
70. **文字サイズは6段だけを使う**（micro 12 / caption 14 / body 16 / subheading clamp(20,2.4vw,26) / heading clamp(28,4vw,40) / display clamp(38,6.4vw,72)）。`_common/components.md` のタイポグラフィ表が正本。**実測で1サイトあたり14〜23種類の文字サイズが混在している**（Refero が公開している DESIGN.md の実例は5段）。11.52px と 11.84px と 12.16px の差は誰にも見えない。**見えない差を並べているのは、段を決めずにその場で rem を書いた結果**であり、それ自体が「設計していない」という見え方になる。`check-style.js` ⑩ が段数を出す。
71. **角丸は「箱 = `var(--r)` / ピル = `999px` / 円 = `50%`」の3種までにする**。2026-09-09 の実測で lila が 8/10/12/16px の4種、tomori が 4/6/8/100px の4種を持っていた。`100px` と `999px`、`3px` と `4px` は見分けがつかない。ピルは `999px` に統一する（`100px` は使わない）。正方形を円にする場合だけ `50%` を使う。`check-style.js` ⑪ が種類数を判定する。
72. **影は1サイトに1種類まで。`0 24px 60px` のような大きな影は使わない**。Refero の実例（Monotype）が持つ唯一の影は `0 0 2px rgba(0,0,0,0.16)` で、実質的に影を使っていない。深い影は 2016 年頃のカードUIの手癖として読まれる。影ではなく `1px solid var(--line)` で分ける（既存の「枠→余白」方針と同じ結論）。
73. **`!important` は `prefers-reduced-motion` ブロックと `[hidden]` の打ち消し以外で使わない**（27の具体化）。2026-09-09、6サイトの `!important` 34件を除去し、**全要素の計算済みスタイルを変更前後で比較して差分0行を確認した**。34件すべてが何もしていなかった。`.hero .button-subtle`（詳細度 0,2,0）は `.button-subtle`（0,1,0）に必ず勝つ。順序ではなく詳細度で決まるため、`!important` は不要だった。効かないときは詳細度と挿入位置（65）を疑う。
74. **デモ注記は日本語で1つだけ、`<p class="demo-note">` で置く**。色は `color: inherit` で footer から継承させる（ハードコードするとフッターの配色を変えたときに取り残される）。2026-09-09 時点で akari / mori / tomori は注記が2つ重複し、うち mori は `SateOn Demo Site`、tomori は `SateOn demo-notice / This page is a concept site...` とクラス名がそのまま本文に出ていた。forge / lila / tsumugi は注記が1つもなく、67 に違反していた。




#### 機械判定する項目と、しない項目

| 判定する | 判定しない（人が見る） |
|---|---|
| 1文60文字 / 見出し20文字（h1・h2） | 文体レベル A/B/C が業態に合っているか |
| 読点（20文字以上打たない / 1文に3個以上） | 同じ主語の2回以上の繰り返し |
| ですます・である の混在（セクション単位） | コンセプト文の具体性テスト |
| 「的」1文2回 / 接続詞の連続 / 誇張語 | |
| 「させていただく」3回以上 / 英語直訳パターン | |
| 漢字ひらがな基準 / 禁止カタカナ | |
| keep-all の設定 / 行頭禁則の実測 | |

**漢字ひらがな基準は曖昧さのない14語のみ判定する。** 「御 / 事 / 物 / 為 / 等 / 様」は事務所・食事・建物・行為・等々・様子 と衝突するため対象外。
**英字テキスト（eyebrow・ブランド表記）は文字数・読点の対象外。** ガイドは日本語コピーの基準。

### 装飾の抑制（54〜58 / 2026-09-08 追加）

> 2026-05-03 に決めた「枠→余白」方針が akari では4か月間守られておらず、
> rules.md に条項はあったのに検査手段がなかったため誰も気づかなかった。
> **ルールは書くだけでは守られない。検査して初めて守られる。**
> 判定は `tools/check-style.js`（qa-check.sh ⑥ / pre-commit で自動実行）で行う。
> 54・55 の判定基準は Refero Design Skill の `anti-ai-slop.md`
> （MIT License / Copyright (c) 2026 Refero / github.com/referodesign/refero_skill）を
> SITEON 向けに翻案した。

54. **操作要素でないブロックに `box-shadow` を付けない**（2026-05-03「枠→余白」変更1・変更2の再確認）。テキストブロック・画像コンテナ・情報カードは、枠ではなく余白と階層で読ませる。影を残してよいのは **ヘッダー / フッター / ナビ / ヒーロー内オーバーレイパネル / フォーム・ボタン等の操作要素** のみ。
55. **意味を持たない側面アクセントストライプを付けない**。`border-left: 3px solid var(--accent)` のような装飾は禁止。側面の太い罫線は **状態・優先度・選択・所有者** を示す場合にのみ使う。**その色が何を意味するか一言で言えないなら外す。** 引用の指示など純粋な体裁目的なら 1px の `var(--line)` で足りる。
56. **インディゴ／バイオレット系（色相 250〜290・彩度0.3以上）をアクセントに使わない**。AI生成デザインの最大の指紋であり、ブランドの要請がない限り使用しない。信頼感が要るなら青系 `#2563eb`、差別化ならティール系 `#0d9488` など、業態から選ぶ。
57. **絵文字をアイコンとして使わない**。SVGアイコンか Unicode記号（→ ・ ◆）を使う。ページ本文に絵文字が混じると、それだけで安っぽく見える。
58. **ライトモードが基準**。業態・ブランドの要請がない限りダーク基調にしない。ダークは意図的なブランド選択であって既定値ではない（barber 等トーンが要請する業態は除く）。

### アクセシビリティ・フォームの検査（2026-09-08 追加）

カテゴリ5「アクセシビリティ（8項目）」のうち、自動検査があったのは 36（タップ領域 / check-mobile.js）だけだった。
31・32・34・35・38 は条項があるのに検査手段がなく、守られているかを誰も確認できていなかった。
`tools/check-craft.js`（qa-check.sh ⑦ / pre-commit で自動実行）で以下を判定する。

| 既存条項 | 検査内容 |
|---|---|
| 31 | スキップナビゲーションの有無 |
| 32 | メニュートグルの `aria-expanded` / `aria-label` / `aria-controls` |
| 34 | `:focus-visible` の定義、`outline: none` の無補償除去 |
| 35 | コントラスト比 4.5:1（背景をアルファ合成して判定） |
| 38 | フォームの label 紐付け |

加えて、Refero `craft-details.md`（MIT）由来の項目を検査する。

59. **入力欄の `type` / `autocomplete` を用途に合わせる**。メールは `type="email" autocomplete="email"`、電話は `type="tel" autocomplete="tel"`、氏名は `autocomplete="name"`。モバイルで適切なキーボードが出て、自動入力も効く。
60. **メール・コード・ユーザー名の欄には `spellcheck="false"` を付ける**。赤波線が出て入力を妨げる。
61. **ペーストを禁止しない**。`onpaste` で `preventDefault` するのはアクセシビリティ違反。

#### コントラスト判定の注意

背景画像の上にある文字と、`position: fixed` / `absolute` で他のコンテンツの上に浮いている文字は、
祖先を辿るだけでは実際の背面色が分からないため**判定不能として除外**し、件数だけ出力する。
それらは目視かシミュレータで確認する。

#### 色変数の設計

**同じ変数を明るい地と暗い地の両方で使わない。** 単一の値では両方で 4.5:1 を満たせない。
siteon.jp では `--text-light`（暗い地用）と `--text-muted`（明るい地用）に分けた。
ブランド色を文字に使う場合も同様に、面用（`--accent`）と文字用（`--accent-text`）を分ける。
**検査を通すためにブランド色そのものを変えない。**

#### 参考: 非インタラクティブなカード数

mori と akari は多い。減らすかどうかは業態とデザイン方針の判断であり、機械的な正解はない。

### オーバーレイ・固定ヘッダー・アンカー（50〜53 / 2026-09-07 追加）

> bloom を iOS シミュレータ（iPhone 17 Pro / iOS 26.5 / Safari）で実機確認した際に検出。
> いずれも横オーバーフロー検査（scrollWidth <= innerWidth）は通過しており、**数値検査だけでは検出できない**。

50. **モバイルナビ等のオーバーレイパネルの背景は完全不透明にする**。`rgba(..., 0.98)` のような「ほぼ不透明」も禁止。背面がヒーロー写真＋白抜き大見出しのような高コントラストだと、**2%の透過でも背面の文字がゴーストとして視認でき**、メニュー項目の可読性が落ちる。意図的に半透明にする場合は、パネル本体を不透明にしたうえで別要素の scrim を敷く。
51. **固定ヘッダー直下に開くパネルの位置は、ヘッダーの実高に追従させる**。`top: var(--header-h)` のような固定px参照は禁止。ヘッダー内テキストが折り返すと実高が変わり、パネルがヘッダーの裏に潜って先頭が隠れる。親の固定ヘッダーを基準に `position: absolute; inset: 100% 0 auto 0;` を使う。
52. **`word-break: keep-all` を当てた要素には `overflow-wrap: normal` を必ず併記する**。`body, body * { overflow-wrap: anywhere; }`（mobile-safety 必須ブロック）を併用していると **`anywhere` が `keep-all` を上書きして語中改行が復活し**、長音符「ー」や句読点が行頭に孤立する。ルール31・47と併せて運用する。
53. **アンカーの `scroll-margin-top` に使う CSS変数は、同一ファイル内で必ず定義する**。未定義変数を含む `calc()` は無効値となり `scroll-margin-top: 0` にフォールバックするため、着地点が固定ヘッダーの裏に完全に隠れる。値はヘッダーの**折り返し後の実高**より大きく取る。

## 5b. アニメーションルール（画像・要素別）

> 原則：**アニメーションの唯一の正当な理由は「視線誘導」**。
> 写真は静止している方が質・信頼感が高く見える。動かす理由がない要素には付けない。

### 画像へのアニメーション：原則禁止

以下の要素への `fade-in` / `translate` 付与を**禁止**する：

- `img` タグ全て
- `figure` / `.image-card` / `.gallery-item`
- `.service-card` / `.strength-card` / `.works-card` / `.gallery-card`
- `.profile-card` / `.portrait-stack` / `.member`
- `.stat-card`（カード全体）
- `.company-gallery` 内の全要素

**禁止理由**：
- `translateY` → グリッド内で隣接要素と視覚的に衝突する（今回発生した崩れの原因）
- 写真・作品は静止している方が重厚感・プロフェッショナル感が出る
- グリッド内で全カードが同時に動くと視線が散乱し、誘導効果がない

### アニメーションを付けて良い要素（限定許可）

| 要素 | 許可アニメーション | 備考 |
|------|-----------------|------|
| セクション見出し `h2` | `opacity` + `translateY(16px)` | 読む順番を作る |
| サブコピー・本文 `p` | `opacity` + `translateY(12px)` | h2より少し遅延させる |
| `section-kicker` | `opacity` のみ | |
| CTAボタン | hover時の `transform: scale` のみ | 既存ルール通り |
| ヒーロー内キャッチコピー | `opacity` + `translateY(20px)` | 最初の登場演出として有効 |
| ナビ・モーダルの開閉 | `opacity` + `transform` | UIフィードバック |

### 例外：単独画像の opacity フェード（条件付き許可）

以下を**全て**満たす場合のみ `opacity` フェード（translateY なし）を許可：
1. グリッド外の単独配置（1カラムで画面幅の50%以上を占める画像）
2. `opacity` のみ（`translateY` 禁止）
3. トランジション 0.8s 以内

### アニメーションが有効なシチュエーション（設計判断の参考）

- ✅ ページ初回表示時のヒーロー文字の登場
- ✅ スクロールで新しいセクションの見出しが現れる
- ✅ 統計数値セクションのカウントアップ
- ✅ フォームの送信完了メッセージの表示
- ✅ ハンバーガーメニューの開閉
- ❌ 既にスクロールして見える位置にある画像
- ❌ グリッド内の複数カードが一斉に動く
- ❌ 作品・料理・建築写真（静止している方が価値が伝わる）

## 16. インフラ・デプロイ品質

> 2026-04-14〜18 の siteon.jp SSL 障害（https_enforced リセット起因）を受けて追加。

### GitHub Pages 変更後の必須チェックリスト

Organization 移管・リポジトリ移動・Settings 変更・カスタムドメイン変更を行った後は、以下を毎回確認する：

1. **Custom Domain が Settings → Pages で設定されているか**
   - 確認コマンド：`gh api repos/{owner}/{repo}/pages --jq '.cname'`
   - 期待値：`"siteon.jp"` のような設定済みドメイン名

2. **CNAME ファイルがリポジトリルートに存在するか**
   - 確認コマンド：`gh api repos/{owner}/{repo}/contents/CNAME --jq '.content' | base64 -d`
   - 期待値：ドメイン名 1 行（改行のみ）

3. **Enforce HTTPS（https_enforced）が true になっているか** ⚠️ 最重要
   - 確認コマンド：`gh api repos/{owner}/{repo}/pages --jq '.https_enforced'`
   - 期待値：`true`
   - **Web UI では気づきにくい設定**。必ず API 経由で確認する
   - false のままだと GitHub は `*.github.io` 用ワイルドカード証明書を返し ERR_CERT_COMMON_NAME_INVALID が発生する

4. **HTTPS で 200 応答があるか**
   - 確認コマンド：`curl -sI https://{domain} | head -1`
   - 期待値：`HTTP/2 200`

5. **証明書の subject が正しいドメイン名か**
   - 確認コマンド：`echo | openssl s_client -servername {domain} -connect {domain}:443 2>/dev/null | openssl x509 -noout -subject`
   - 期待値：`subject=CN = {domain}`（例：`CN = siteon.jp`）
   - `CN = *.github.io` が返ってきたら https_enforced が false の可能性

### トリガー条件（このチェックをいつ実行するか）

以下の作業を行った場合、**直後に必ず全 5 項目を実行**する：

- Organization 移管（y1-310 → novatech-studio 等）
- リポジトリ名変更
- Settings → Pages の設定変更（Source ブランチ変更・Custom domain 追加/削除含む）
- CNAME ファイルの編集
- Xserver 等の DNS レコード変更
- カスタムドメインの新規追加

### 月次保守での定期実行

毎月 1 日に `tools/github-pages-health-check.js` を実行し、全クライアントサイトの状態を Slack `#alerts` に報告する。

### 異常検知時の対応手順

`https_enforced = false` が検出された場合の修復手順：

```bash
# Custom Domain 再設定（証明書プロビジョニングを再トリガー）
gh api -X PUT repos/{owner}/{repo}/pages -f cname="" && \
gh api -X PUT repos/{owner}/{repo}/pages -f cname={domain} -F https_enforced=true
```

修復後、10〜60 分待機して上記チェックリスト 5 項目で再確認する。

### 禁止事項

- Web UI 確認だけで「設定済み」と判断しない（https_enforced が見えにくい）
- Let's Encrypt 証明書再発行中（10〜60 分）に設定を何度も変更しない
- DNS 変更は必ず Yuichi に依頼（Xserver は手動操作必須）

### 事故事例（教訓）

- **2026-04-14〜18**：Org 移管作業中に https_enforced がリセット → siteon.jp 4 日間閲覧不可
- 遅延理由：Custom Domain・CNAME・DNS はすべて正常に見え、Web UI 上も「Your site is live」と表示されていた

## 22. commit前セルフチェック（v2 — 再修正ゼロを目標とする）

### 原則
Yuichiから同じフィードバックを2回以上もらうことは許容しない。
1回で正しく実装し、1回で正しくチェックする。

### Phase 1: 実装前の確認
1. 指示文の全項目をリストアップし、番号を振る
2. 各項目について「何を」「どこの」「どう変えるか」を具体的に言語化する
3. 対象要素を grep / 検索で全て洗い出す（ヘッダー・フッター・セクション内を漏らさない）

### Phase 2: 実装中の確認
1. 1項目実装するごとに、変更が反映されているか grep で即時確認
2. CSSの場合: セレクタの詳細度（specificity）が既存スタイルに勝っているか確認
3. レイアウト変更の場合: display / grid-template / flex の旧指定が残っていないか確認
4. !important が必要な場合は明示的に付与

### Phase 3: commit前の最終確認
指示文の全項目を1つずつチェックし、以下の形式で結果を記録:

項目1: [指示内容] → grep結果: [具体的な出力] → ✅ or ❌
項目2: [指示内容] → grep結果: [具体的な出力] → ✅ or ❌
...

1項目でも ❌ があればcommitしない。原因を特定して再修正。

### 改行（<br>）チェック
指示で改行位置が指定された場合、以下を必ず実施:
1. grep で <br> の前後の文字列を確認し、指示通りの位置にあること
2. フォントサイズ × 文字数 × letter-spacing を計算し、改行前のテキストがコンテナ幅に収まることを数値で証明
3. 収まらない場合は font-size を clamp() で調整してから commit
4. word-break: keep-all を適用し、意図しない折り返しを防止

### Phase 4: push後の公開確認
1. curl で公開HTMLを取得
2. Phase 3 と同じチェックを公開HTML上で再実行
3. ファイルサイズが前回比で極端に増減していないか確認
4. .nojekyll の存在確認

## 23. デモサイト改修の教訓DB（2026-05-04）

### デザイン原則
- border囲みの多用は安っぽく見える → 余白・背景色差・下線で代替
- ボタンの border-radius: 2px は肉眼でほぼ見えない → 8px がモダンで適切
- 情報カード（営業時間・料金・電話番号・住所）はデモサイトに不要 → §21準拠で削除
- 横スクロールティッカー（marquee）はダサい → 削除
- 写真の上にテキストオーバーレイは読みにくい → 写真の下にテキスト配置 or テキスト削除
- Conceptセクションは1カラム構成が基本 → 2カラムで右を空にしない
- ボタンサイズは全ページで統一（padding: 1rem 2.5rem, font-size: 0.85rem, letter-spacing: 0.1em）

### 削除操作の安全ルール
- テキスト要素を削除する際、親要素ごと消さない → img等の兄弟要素を巻き添えにしない
- 削除前に grep "<img" で画像数をカウント → 削除後に同数であることを確認
- figcaption のテキストだけ消す場合: テキストノードのみ削除、<figcaption>タグ自体は残してもよいが<img>は絶対に消さない

### 改行（<br>）の実装ルール
- <br> を挿入するだけでは不十分 → フォントサイズ × 文字数 × letter-spacing がコンテナ幅に収まるか計算必須
- word-break: keep-all を日本語テキストに適用 → 意図しない位置での折り返しを防止
- clamp() でレスポンシブ対応 → PC/タブレット/モバイルで計算

### GitHub Pages 運用
- .nojekyll は全リポ必須 → Jekyll が inline CSS/JS の {} を Liquid として誤解釈・削除する
- assets/ を git add し忘れると画像が全て 404 → commit前に git status で未追跡ファイルを確認
- push 後に curl でファイルサイズを確認 → 極端に小さい場合は Jekyll 破損の疑い

### AI画像生成の品質ルール
- 業態と人物の性別を一致させる（バーバー→男性の手、ネイル→女性の手）
- ギャラリーのスタイル名と画像内容を一致させる（SKIN FADEのラベルにCLASSICの写真を使わない）
- 正面顔はリアリティ条件を全て適用（§20参照）
- 写真内にテキスト・ロゴ・透かしを入れない

以下のいずれかに該当する場合に実行:

1. JavaScript（予約UI・タブ切り替え・ハンバーガーメニュー等）を新規実装または大幅修正した時
2. レスポンシブ（@media）を大幅に書き換えた時
3. 外部API連携（Formspree・Instagram API等）のコードを変更した時

実行コマンド（フォーカスを指定して実行）:
```
/codex:adversarial-review --wait iOSサファリでの動作、アクセシビリティ、レスポンシブ崩れを重点的に確認
```

### /codex:rescue の使用ルール

以下の条件で使用する:

1. Codex CLIへの出力委任（HTMLサイト生成、大量テキスト生成等）
2. 既存の `script -q /dev/null codex -a never` の代替として使用可能
3. 軽いタスクは `--model gpt-5.4-mini` でコスト節約

実行例:
```
/codex:rescue --background --model gpt-5.4 このindex.htmlのFlowセクションをスマホ対応に修正してください。修正要件: ...
```

### 使用禁止の場面

- 秘書室のNotion操作（プラグインの管轄外）
- git push / deploy 操作（CEOが直接実行すべき）
- API キーや認証情報を含む作業

### レビュー結果の扱い

- /codex:review の結果で「重大な問題」が報告された場合 → 修正してから Yuichi に報告
- /codex:review の結果で「軽微な提案」のみの場合 → そのまま Yuichi に報告（レビュー結果を添付）
- /codex:adversarial-review の結果は必ず Yuichi への報告に含める
