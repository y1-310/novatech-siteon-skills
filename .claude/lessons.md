# Lessons Learned（修正パターン記録）

## 1. 元のHTML/デザインを勝手に変更しない
- **状況**: WordPressテーマ化の際にナビを日本語化、セクション追加、ボタンテキスト変更など余計な変更を加えた
- **結果**: ユーザーが期待するデザインと異なるものになった
- **ルール**: 元のHTML/Figmaデザインを忠実に再現する。変更が必要な場合は事前に確認する

## 2. プリセットのCSS変数を勝手に変更しない
- **状況**: 元のHTMLがTailwind CSSを使用していたのに、独自CSSに書き直した
- **結果**: デザインが完全に崩れた
- **ルール**: プリセットで定義されたCSS変数（--bg/--accent等）の値を勝手に変更しない。変更が必要な場合は事前に確認する

## 3. wp_enqueue_scriptでTailwind CDNを読み込まない
- **状況**: WordPressの`wp_enqueue_script`でTailwind CDNを読み込んだ
- **結果**: configスクリプトとCDNの読み込み順序が保証されず、カスタムカラーが効かない
- **ルール**: Tailwind CDNとconfigは`header.php`に直接記述する（WP案件用）

## 4. GitHubが最新版とは限らない
- **状況**: GitHubのHTMLを最新版と思い込んだ
- **結果**: localhostで動いている版と比較して確認が必要だった
- **ルール**: 最新版がどこにあるか必ずユーザーに確認する

## 5. 量産時はスキル＋プリセットで品質担保
- **状況**: サイトを量産する際、毎回ゼロからUI設計するとクオリティにバラつきが出る
- **結果**: UI品質の不安が制作スピードのボトルネックになる
- **ルール**: スキルの参照ファイル＋カラープリセットを使用して品質を安定させる。業態別スキル（lp-salon/lp-barber等）で構造を統一し、プリセットで差別化する

## 6. コード記述は Claude Code、監査は Codex（役割反転）
- 2026-09-07 役割反転。月凪比較検証(2026-04-24)でCC+skill 85点/コード品質85点を確認。記述=Claude Code、監査=Codexに変更

## 7. Chromiumの数値検査を通っても実機では崩れる（メニュー展開状態は無検査だった）
- **状況**: bloom を mobile-preview v1.2 で10ビューポート検査し、横オーバーフロー0pxで「問題なし」と報告した
- **結果**: iOSシミュレータで開いたところ、ナビパネルの背面透け・ヘッダーの長音符孤立・アンカーの着地ズレの3件が即座に見つかった。いずれも横オーバーフロー検査では原理的に検出できない
- **原因**: 検査が「初期表示・閉じた状態・横幅のみ」に限定されていた。メニュー展開状態、アンカー遷移後、行頭禁則は一度も測っていなかった
- **ルール**: 数値検査の通過を「問題なし」と報告しない。**インタラクション後の状態（メニュー展開・アンカー遷移）を必ず1度は実機またはシミュレータで見る**。検査項目は rules.md カテゴリ4「メニュー展開状態の検査」チェックリストに従う
- **補足**: `rgba(..., 0.98)` は背面が高コントラストだと肉眼で透けて見える。「ほぼ不透明」は不透明ではない（rules.md 50）

## 8. アニメーション途中のスクリーンショットを不具合と誤認しない
- **状況**: iOSシミュレータで `#access` / `#staff` を開き、見出しを行き過ぎた位置が写ったスクリーンショットを見て「iOS Safari 固有のアンカー着地ズレ」と報告した
- **結果**: 実在しない不具合を「原因未特定の未解決事項」として秘書ノートに記録してしまった。実際にはサイト側の欠陥はゼロ
- **原因**: 全デモサイトが `scroll-behavior: smooth` を設定しており、Safari はアンカーへ**約1秒かけてスクロールする**。`open_url` の直後にスクリーンショットを撮ったため、アニメーションの途中が写っていた。計測を画面に出すデバッグ版で確認したところ `sY=0 → 2623 → 6547 → 7971`、`tgtTop=8072 → 5449 → 1522 → 98` と収束しており、最終着地は正しかった
- **ルール**: **状態が動いている最中に撮った1枚を根拠に判定しない。** アニメーション・トランジション・スムーススクロールが絡む箇所は、収束を待つか、時系列の数値を取って収束を確認してから判定する
- **ルール**: 実機で「おかしい」と思ったら、断定する前に**計測値を画面に出すデバッグ版をローカルサーバーで配信して数値で確かめる**。シミュレータのSafariはJSを直接叩けないが、この方法なら数値が読める
- **補足**: Chromium(Playwright)側は `networkidle` + 待機を挟んでいたため最初から正しい値(98〜101px)を返していた。「実機とChromiumで食い違う」と考えた時点で、まず自分の計測方法を疑うべきだった

## 9. ルールは書くだけでは守られない。検査して初めて守られる
- **状況**: 2026-05-03 に「枠→余白」改修（カードの border / box-shadow 削除）を全8サイトへ横展開したと記録していた
- **結果**: 2026-09-08 に検査ツールを作って当てたところ、**akari では4か月間まったく守られていなかった**。`.statement` は白背景+影+左3pxストライプのまま、`.image-card` にも影が残っていた
- **なぜ気づかなかったか**: rules.md に条項はあったが、**機械的に検査する手段が一つもなかった**。私自身が同じサイトを2回レビュー（rules.md準拠のレビューとレイアウトの実測レビュー）しても発見できていない。目視と読み合わせでは装飾の残存は見つからない
- **ルール**: **横展開したルールには、必ず同時に検査手段を用意する。** 検査できないルールは「守られているつもり」になるだけで、実態は守られない
- **ルール**: 既存ルールを守っているかを問うときは、条項を読み直すのではなく**検査ツールを書いて数える**
- **対応**: `tools/check-style.js` を新設し `qa-check.sh` ⑥ に組み込んだ（pre-commit で自動実行）。妥当性は3段階で検証済み — 枠→余白改修前(v3.1) 21件 / 改修後の取りこぼし状態 5件 / 修正後 0件
- **補足**: 検出項目の一部は Refero Design Skill の anti-ai-slop.md（MIT）を翻案した。**無料の手法ファイル1本で実バグ3件が出た。** 有料契約の前に、無料で試せる範囲を先に使い切る

## 10. iOS Safari は `word-break: keep-all` を CJK に効かせない。Playwright の WebKit では再現しない（2026-09-11）

siteon.jp の本文に `word-break: keep-all` + `overflow-wrap: break-word` を当てたところ、
Chromium では読点で折り返すのに、iPhone 17 Pro のシミュレーター（実 iOS Safari）では
語中で折れた。同じURL・同じインラインCSS・同じ 402pt 幅で、1行に入る文字数が
11文字 と 23文字 で倍近く違う。

**Playwright の WebKit を入れて確かめたが、そちらは Chromium と同じ位置で折れた。**
つまり「WebKit で検査すれば捕まえられる」わけではない。Playwright の WebKit は
WebKit trunk の独自ビルドで、iOS Safari とは挙動が違う。

### ここから引く教訓

- **エンジン差を疑ったら、まず再現手段を確かめる。**「WebKit で検査すればよい」と
  結論を出す前に、その WebKit が本当に同じ挙動をするかを確認する。
  私は確認前に「検査が Chromium だけなのが問題」と報告してしまい、正確でなかった。
- **`keep-all` に依存した設計は iOS では保証されない。** ルール63・64 は keep-all を
  前提にしているが、成り立つのはデスクトップだけ。iOS では通常のCJK改行になる。
- ただし **これは不具合ではない。** 語中で折るのは日本語組版として普通で、
  禁則（句読点が行頭に来ない）は `line-break: strict` が iOS でも効いている。
  keep-all は「デスクトップでより良く見せる上乗せ」として扱い、
  これが効くことを前提に設計しない。
- **実機で見ないと分からないことがある。** 今回は9つの自動検査が全て通ったうえで、
  シミュレーターで初めて見えた。
